# Working with skills and extended memory

This machine has two places to put knowledge, and picking the wrong one makes the
knowledge disappear. Read the first section before writing anything.

## Fact or procedure

**A fact goes to extended memory.** *"The GitLab backup runs at 04:31."* *"We chose
socket activation because the service starts before the network."* Memory costs
nothing while idle and is found by semantic search — it is the right home for
history, decisions, and reasons.

**A procedure goes to a skill.** *"When a k3s node is NotReady, do these steps."*
A skill's name and description load on every single message; its body loads only
when something matches. It is the right home for a method.

The two expensive mistakes:

- **A procedure written as memory** only surfaces if someone happens to search the
  right words. Nobody does that mid-incident.
- **A fact written as a skill** inflates every message forever and fires on
  questions it cannot answer.

If you cannot decide: does it answer *"how do I do X?"* (skill) or *"what is true
about X?"* (memory)? When in doubt, memory — a misplaced fact is cheap to move, a
misplaced skill costs context on every turn.

## Auditing skills

Run `/audit-skills`. It measures every installed skill and prints a table. Then:

1. **Report the table as printed.** Do not summarise it into prose.
2. **Fix `NEVER SAYS WHEN` first.** A description that says what a skill is but not
   when to use it means the skill can never fire — it is paid for on every message
   and never used.
3. **Turn off what is unused, do not delete it.** State this explicitly; people
   hesitate to touch skills. Disabled costs nothing; deleted costs the memory of
   having written it.
4. **Open any skill flagged `SHIPS CODE` before letting it run again.**

The number that matters most is the startup cost: what all skills together charge
on every message whether they fire or not.

Run it again after importing anything. Imported material has never been measured.

## Extended memory

**Search before answering.** Anything about past events, earlier decisions, or
infrastructure that is already running:

```
/recall <question>
```

Ground the answer in what came back and **name the source file**. A note can be
stale; the live system outranks it. When they disagree, say both and say which you
trust — do not quietly pick one.

**Save when a future session would otherwise rediscover it.** `/remember <title>`,
with the note on stdin:

```markdown
# What this note is about

## Context
What was going on, and what forced the decision.

## What was done
The command, the config, the change — concrete and copy-pasteable.

## Why
The reason. Without this it is a recipe with no reasoning, and it rots silently.
```

Then check:

- **H1, then H2 sections.** The indexer chunks on headings; a heading-less note
  becomes one diluted blob and stops being findable.
- **One fact per note.** Two facts in one file means searching for either drags in
  the other.
- **The answer, not the investigation.** What worked, not everything you tried.
- **Category that actually exists** — look inside the knowledge base before
  inventing one.
- **If a note already covers it, patch that note.** A second copy will drift from
  the first, and then neither can be trusted.
- **Never write a secret.** No keys, tokens, passwords, private keys. Say where the
  credential lives, never what it is.

If `/recall` returns nothing, say the base has nothing on it. Do not substitute a
guess that reads like a finding.

## Capturing a new skill

Write it when a procedure repeats, or when you just worked something out that is
worth doing the same way next time.

Placement: `~/.claude/skills/<name>/SKILL.md`.

**The description is the whole ballgame.** Only name and description load at
startup; the body loads if the description matches. So the description must say
*when*, not just *what*:

```yaml
---
name: k3s-wedged-node-recovery
description: Use when a k3s node is NotReady, unreachable, or stuck in a reboot loop. Diagnoses from the control plane before touching the node.
---
```

Weak: `description: Notes about k3s nodes.` — never fires.
Strong: starts with **"Use when …"**, names the symptoms the operator would type,
and says what the skill does about them.

Body rules:

- **Under 500 lines and 5,000 tokens.** Past that, move branch-specific material
  into `references/` and point to it — the agent opens it only when needed.
- **Imperative, second person.** "Run the script", not "the script should be run".
- **Every command runnable as written.** A placeholder that is not obviously a
  placeholder will be executed literally.
- **State the pitfall you actually hit.** That is the part the model cannot derive.
- **No credentials, no customer data, no transcript dumps.**

After writing it, run `/audit-skills` and fix anything it flags. A new skill that
never fires is not a skill, it is a tax.

## Importing from another agent

`/import-skills --from <agent> --list` shows what exists without writing anything.
Nothing is read unless the source is named.

When reporting the result, surface the warnings instead of swallowing them:
converted rules are lossy, and an `alwaysApply` rule that became a skill no longer
applies to everything.

## Distilling a finished session

`/distill-status` shows the queue; `/distill-now` forces a job. Distillation is how
a session becomes a skill without you writing it by hand. It only runs when a
headless model is configured — if `/distill-status` says it is not available, say
so plainly rather than implying a job is running.

Review what it produced with `/audit-skills` like any other new skill.

## Rule that keeps this from rotting

**Measure, do not estimate.** Counts and token sizes come from
`.claude/smartclaude` scripts, never from your own arithmetic — you will get a
different answer each time you try. If a script failed, say it failed. An audit you
did not run is not an audit.
